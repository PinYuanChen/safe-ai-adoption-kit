messages 是怎麼長大的

一句話：模型是金魚，沒有記憶。每次呼叫 create() 都要把整段對話從頭重送一次，所以 messages 會一輪一輪變長。

背景

測試裡要檢查 client.calls[1]["messages"][2]["content"][0]。這一串索引看起來像密碼，其實只要知道 messages 每一輪長什麼樣子就懂了。

觀念

以「HL-10421 出貨了嗎？」為例

拆解那串密碼

client.calls[1]["messages"][2]["content"][0]
#           │        │      │       │     └ 第一個區塊 → 那個 tool_result dict
#           │        │      │       └ 這則訊息的內容（list）
#           │        │      └ 第 3 則訊息 → user 送回的工具結果
#           │        └ 送出的整段對話
#           └ 第 2 次呼叫

三條鐵律

規則為什麼
role 要 user、assistant 輪流模型是照輪流的 turn 訓練的。連續同 role 的訊息不會被拒絕，而是被合併成一個 turn
這一輪的 tool_result 全放同一則 user 訊息要緊接在 tool_use 後面。拆開的話，文件說會「教」模型少用平行呼叫
tool_result 放在 user 訊息裡在 API 眼裡，工具結果是「你」回報給模型的
assistant 那則要原封不動送回包括開場白的 TextBlock，模型才看得到自己說過的話
tool_use_id 要等於對應的 id一則回覆可能有好幾張點菜單，靠 id 對上哪道菜是哪張單的

踩雷紀錄

更正（2026-11-05）：連續的 user 不會被拒絕
這裡原本寫「連續兩則 user 會被拒絕」，是沒查文件就寫的。Messages API 文件寫的是合併成一個 turn。驗收 session 抓到的。
為什麼 FakeClient 要 deep copy？
run_agent 一直往同一個 messages list 加東西。如果 calls[0] 只存參照，事後打開會看到三則訊息，而不是當時真正送出的一則。deep copy 就像當下拍照存證，之後怎麼改都不影響照片。
