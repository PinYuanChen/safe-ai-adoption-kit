信任邊界：模型給的東西，進門要查

一句話：input_schema 裡的每個欄位，都要假設是不可信的人填的。第一個碰到它的地方就要驗，驗不過就退件，不要幫它修。

背景

三個問題其實是同一件事：

  • orders 為什麼不放進 input_schema？我的答案是「會多花 token」，只對了一小半。
  • order_id 的判斷要放在哪裡？
  • 模型傳數字的話，我是不是該強制轉成字串？

觀念

邊界畫在哪裡

input_schema 是模型要填的表單

它不是「要傳給模型的資料」，而是「模型呼叫工具時要自己填的欄位」。把 orders 放進去，等於要模型自己生出訂單資料：

  1. 模型根本沒有這些資料，只能憑空編造，函式就會在假資料裡「查到」假結果。
  2. 模型填的值可以被操控，使用者或注入的文字都可能影響它。資料來源交給模型，等於讓攻擊者決定 tool 回傳什麼。

token 主要花在 tool_result：查詢結果會整包送回去給模型讀。那是回傳值要考慮的事，跟 input_schema 是兩回事。

先認 tool，再驗參數

if 名稱是 lookup_order:
    檢查 order_id 在不在
    檢查 order_id 是不是字串
    執行 lookup_order
else:
    不存在的 tool

order_id 是 lookup_order 專屬的參數。先確認它是什麼，再去讀它才有的東西。

拒絕，不要幫它修

str(12345)          # "12345"，沒有 HL-，照樣查不到
str(None)           # "None"
str(["HL-10421"])   # "['HL-10421']"
str({"x": 1})       # "{'x': 1}"

什麼都能轉成字串，所以什麼都會被放行。

做法模型得到的訊息結果
強制轉字串「查不到訂單」錯誤的結論：訂單不存在
拒絕並回報「order_id 要是字串，收到 int」模型修正後重查

tool_result 也是外部輸入

role 是從模型的角度分的：assistant 是它自己說的話，user 是所有從外面送進來的東西。所以 tool 結果和使用者打的字，對模型來說是同一個等級。如果資料裡藏了「忽略之前的指示」，模型讀到時就像使用者親口說的。這是 Component 3 要測的 prompt injection。

踩雷紀錄

驗證順序反了，訊息說錯 tool
order_id 的檢查放在名稱判斷之前，結果每個 tool 都被拿來檢查 order_id： 
cancel_order {}  -> lookup_order is missing the required 'order_id' argument.
search_orders {'customer': 'Copperleaf Home Goods'}  -> lookup_order is missing ...
模型叫的明明不是 lookup_order。當時 17 個測試全綠，因為唯一的 cancel_order 測試有帶 order_id，剛好避開了。
refactor 順手拿掉了 block.type 檢查
抽出 run_tool 時，迴圈變成把每個區塊都丟進去。模型先說一句話再叫 tool 時就當掉了：AttributeError: 'TextBlock' object has no attribute 'name'。當時 15 個測試全綠，因為沒有任何測試的回應裡有文字區塊。測試只保護它涵蓋到的行為，所以補了回歸測試。
已知問題，先記著：IDOR
自動安全審查標記了 lookup_order：拿到任何編號都回傳整筆訂單，不檢查問的人有沒有權限。編號是連號的，猜起來很容易。使用者身分要從伺服器端傳進來，不能放進 schema。目前 agent 還沒有「使用者是誰」的概念，留給 Component 3、6。
