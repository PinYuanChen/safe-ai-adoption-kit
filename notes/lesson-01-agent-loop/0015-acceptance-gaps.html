NOTE 0015第 1 課驗收待問答驗收2026-11-05

測試全綠，然後驗收說：還沒做完

一句話：全綠只代表「我寫的測試都過了」，不代表「該做的都做了」。max_tokens 和 MAX_TURNS 都不是成本上限，要自己累加 usage。

背景

27 個測試全綠、PR 也 merge 了，連筆記都寫了「Component 1 完成」。回到課程那邊的 session 驗收，它對照講義和程式碼，列出了 token 預算和截斷重試都沒做，也沒有截斷 tool_use 的測試。

觀念

三個上限，各管各的

上限管什麼管不到什麼
max_tokens單次回應的輸出長度輸入；而且每一圈都重新拿一份額度
MAX_TURNS圈數每一圈有多貴
TOKEN_BUDGET整場累計的 input + output（這才是成本那道）

每一圈都要重送整段歷史，所以圈數不多也可能很貴。我的真實 log 裡一題大約 2,000 tokens（第 1 題 657 + 55 + 958 + 151 = 1,821），所以 TOKEN_BUDGET 先設 10,000，約是正常用量的 5 倍。

每一圈的判斷順序

截斷的回應為什麼要整則丟掉

tool_use 的 input 可能只寫了一半，例如 HL-1。執行它等於拿殘缺的參數去做事。所以不執行、不 append，用同一份 messages 重送。被丟掉的回應一樣要付錢，也算進預算和回合數，所以重試一定要有上限：這裡是 4096 → 8192，只重試一次。

怎麼證明 tool 真的沒被執行：SpyOrders

class SpyOrders:
    def __init__(self):
        self.was_read = False

    def __iter__(self):
        self.was_read = True
        return iter([])

run_tool 的 try / except 會接住錯誤，光看有沒有爆炸分不出 tool 跑過沒有。這個假資料來源只記一件事：有沒有人走訪過我。

測試的測試：故意改壞 code

測試一寫就通過時，怎麼知道它有在顧門？在暫時的副本裡故意改壞 code，看哪個測試會紅。這叫 mutation testing。這次試了 10 種：

故意改壞結果
結果拆成多則 user 訊息抓到
拿掉預算檢查 / 預算移到 end_turn 前抓到
沒累加 output tokens / 每圈歸零抓到
重試沒上限 / 沒調高 max_tokens抓到
截斷的回應 append 進 messages / 執行截斷的 tool抓到
重試移到預算檢查之前沒抓到，補了測試之後才抓到
