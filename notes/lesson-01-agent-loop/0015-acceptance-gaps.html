NOTE 0015第 1 課驗收已驗收2026-11-05

測試全綠，然後驗收說：還沒做完

一句話：全綠只代表「我寫的測試都過了」，不代表「該做的都做了」。max_tokens 和 MAX_TURNS 都不是成本上限，要自己累加 usage。

背景

27 個測試全綠、PR 也 merge 了，連筆記都寫了「Component 1 完成」。回到課程那邊的 session 驗收，它對照講義和程式碼，列出了 token 預算和截斷重試都沒做，也沒有截斷 tool_use 的測試。

觀念

三個上限，各管各的

上限管什麼管不到什麼
max_tokens單次回應的輸出長度輸入；而且每一圈都重新拿一份額度
MAX_TURNS圈數每一圈有多貴
TOKEN_BUDGET整場累計的 input + output（這才是成本那道）

每一圈都要重送整段歷史，所以圈數不多也可能很貴。我的真實 log 裡一題大約 2,000 tokens（第 1 題 657 + 55 + 958 + 151 = 1,821），所以 TOKEN_BUDGET 先設 10,000，約是正常用量的 5 倍。

每一圈的判斷順序

截斷的回應為什麼要整則丟掉

tool_use 的 input 可能只寫了一半，例如 HL-1。執行它等於拿殘缺的參數去做事。所以不執行、不 append，用同一份 messages 重送。被丟掉的回應一樣要付錢，也算進預算和回合數，所以重試一定要有上限：這裡是 4096 → 8192，只重試一次。

怎麼證明 tool 真的沒被執行：SpyOrders

class SpyOrders:
    def __init__(self):
        self.was_read = False

    def __iter__(self):
        self.was_read = True
        return iter([])

run_tool 的 try / except 會接住錯誤，光看有沒有爆炸分不出 tool 跑過沒有。這個假資料來源只記一件事：有沒有人走訪過我。

測試的測試：故意改壞 code

測試一寫就通過時，怎麼知道它有在顧門？在暫時的副本裡故意改壞 code，看哪個測試會紅。這叫 mutation testing。這次試了 10 種：

故意改壞結果
結果拆成多則 user 訊息抓到
拿掉預算檢查 / 預算移到 end_turn 前抓到
沒累加 output tokens / 每圈歸零抓到
重試沒上限 / 沒調高 max_tokens抓到
截斷的回應 append 進 messages / 執行截斷的 tool抓到
重試移到預算檢查之前沒抓到，補了測試之後才抓到

踩雷紀錄

「完成」喊得太早
這一路的步驟是 Claude 排的，它沒有對照講義，就跟我說 Component 1 完成了。講義的檢查清單明明列了 token 預算和截斷重試。完成的定義要來自需求，不是來自「我們原本排了哪些步驟」。
筆記 0011 教錯了一件事
當時寫「max_tokens 再問也不會改變結果」。同樣的請求再送一次確實沒用，但調高 max_tokens 就可能成功。已在 0011 更正。
usage 被排到了 Component 4
筆記 0010 原本把 usage 全部歸給 Telemetry。但 Telemetry 只是把數字記下來，能讓迴圈停下來的是迴圈自己。

一路陪寫的人，容易跟著同一份路線一起漏掉同一件事。這次是另一個帶著講義的 session 才抓到的。

2026-11-07 更新：截斷重試接上真的模型

FakeClient 只會照劇本演，所以暫時把上限調小，故意讓真的模型被截斷。以下都是 observed，每種設定只跑一次。跑完已把數字改回 4096 和 8192。

實驗 A：MAX_TOKENS = 30，截斷後重送成功

[model] stop_reason=max_tokens tool_calls=['lookup_order({})'] input_tokens=657 output_tokens=30
[model] stop_reason=tool_use tool_calls=['lookup_order({"order_id": "HL-10421"})'] input_tokens=657 output_tokens=55
[model] stop_reason=max_tokens tool_calls=[] input_tokens=958 output_tokens=60
[model] stop_reason=max_tokens tool_calls=[] input_tokens=958 output_tokens=120
[model] stop_reason=end_turn tool_calls=[] input_tokens=958 output_tokens=174
  • 截斷的 tool_use 真的會出現：這次的參數是空的 {}，我的測試用的是寫到一半的 HL-1。程式沒有執行它，第 2 次才拿到完整參數。
  • 「整則丟掉」有做對：第 1、2 次的 input 都是 657，第 3、4、5 次都是 958。如果截斷的回應被 append 進去，input 就會變大。
  • 丟掉的回應一樣要付錢：總共 4,627 tokens，其中第 1、3、4 次的 2,783 tokens（約 60%）花在丟掉的回應上。0014 的正常情況是 1,821 tokens，這次約 2.5 倍。
  • 差點撞上 MAX_TURNS：第 5 次才拿到答案，也是最後一次機會。重試也算回合數。

實驗 B：MAX_TOKENS_CEILING = 60，上限擋得住

[model] stop_reason=max_tokens tool_calls=['lookup_order({})'] input_tokens=657 output_tokens=30
[model] stop_reason=tool_use tool_calls=['lookup_order({"order_id": "HL-10421"})'] input_tokens=657 output_tokens=55
[model] stop_reason=max_tokens tool_calls=[] input_tokens=958 output_tokens=60
AgentLoopError: stop_reason: max_tokens on turn 3

第 2 次用 60 成功呼叫 tool，第 3 次還是 60，又被截斷，這時已經到天花板，所以停下來。驗收 session 原本預期會在 turn 2 停，實際是 turn 3。調高後的 max_tokens 會留到這次執行結束，所以天花板管的是整次執行，不是每一輪各算各的（inference，依程式和 log 推得）。

順便確認：平行呼叫

[model] stop_reason=tool_use tool_calls=['lookup_order({"order_id": "HL-10421"})', 'lookup_order({"order_id": "HL-10429"})'] input_tokens=665 output_tokens=107
[model] stop_reason=end_turn tool_calls=[] input_tokens=1096 output_tokens=180

同一則回覆叫了兩個 tool，兩筆結果都有回答到，也沒有對調。

這幾次沒有證明的事
每種設定只跑一次，所以不能說截斷的參數每次都是 {}。累計也都沒超過 10,000，TOKEN_BUDGET 的分支還沒在真的 API 上觸發過。
