解剖室：response、tool 定義、tool_result

一句話：三樣東西、三種方向。response 是模型給你的（物件），tool 定義是你給模型的菜單（dict），tool_result 是你端回去的菜（dict）。

背景

寫 loop 時一直在猜「這裡面到底有哪些欄位」。這篇把它們一個個剖開。

觀念

① response：模型的回覆

stop_reason白話你的 loop 該做什麼
end_turn「我講完了」取文字、回傳
tool_use「麻煩幫我查一下」跑工具、再問一輪
max_tokens「我話還沒說完就被掐斷了」raise，答案不完整
refusal「這個我不能回答」raise

② tool 定義：給模型看的菜單

LOOKUP_ORDER_TOOL = {
    "name": "lookup_order",       # 菜名：要跟 run_tool 裡比對的一字不差
    "description": "...",         # 菜色介紹：模型靠這段決定要不要點、怎麼點
    "input_schema": {             # 點菜規則（JSON Schema）
        "type": "object",
        "properties": {"order_id": {"type": "string", "description": "..."}},
        "required": ["order_id"],
    },
}

description 是你跟模型溝通的唯一管道。你在裡面寫了「只給 5 位數就自己補 HL-」、「查不到就照實說，不要猜」，這些話直接決定模型的行為。寫菜單要像寫給一個很聰明、但第一天上班的新人。

③ tool_result：端回去的菜

  • content 要是字串，所以 lookup_order 回傳的 dict 要先 json.dumps 打包成 JSON 文字。
  • lookup_order 查不到時回傳 {"error": "Order not found", ...}，不是 is_error。對模型來說，「查了，沒這筆」是一道正常的菜，只是菜名叫「沒貨」。

踩雷紀錄

tool_use_id 對不上
真的 API 會直接拒絕下一次請求。FakeClient 不會檢查這件事，所以要靠測試 assert tool_use_id。
