第一次接上真的模型：FakeClient 看不到的事

一句話：FakeClient 證明我的迴圈寫對了；只有真的模型，才看得出它實際會怎麼用這個迴圈。

背景

測試全綠，但 FakeClient 叫它說什麼它就說什麼。模型到底會不會叫 tool、會不會補上 HL-、會不會編造內容，都要跑一次才知道。我也一度搞不清楚金鑰要放哪裡、指令要在哪裡跑。

觀念

金鑰走的路

每次呼叫都看得到：TracingClient

run_agent 只回傳最終答案。cli.py（Claude 寫的 scaffolding）在 client 外面包一層，每次呼叫模型就印一行到 stderr，我的 run_agent 完全不用改：

[model] stop_reason=tool_use tool_calls=['lookup_order({"order_id": "HL-10421"})'] input_tokens=657 output_tokens=55

六題的結果

問題回合模型做了什麼結果
HL-10421 出貨了嗎2查一次，回答出貨資訊資料全對
HL-10429 出貨了嗎2查一次，說查不到沒有編造訂單內容
order 10421 的狀態2自己補上 HL-description 有效，但說太多（見踩雷）
你能幫我做什麼1沒叫 tool，直接回答正確
取消 HL-104252先查訂單，再說做不到沒假裝成功，但多查了一次（見踩雷）
HL-10421 和 HL-104292同一則回覆叫兩個 tool結果沒對調，API 也接受了格式

最後一題是最有價值的驗證：tool_use_id 對不上，或結果沒放在同一則 user 訊息裡，API 會回 400。它接受了，代表 tool_results 的組法是對的。查不到的 dict 裡帶 order_id，也正好用在這個情境。

token 花在哪裡

問題第 1 次 input第 2 次 input
HL-10421（整筆訂單）657958
HL-10429（查不到）657740
  • 每次呼叫都先付約 650 個 input tokens，問題很短，大部分是 tool 定義。打招呼那題也一樣。
  • 整筆訂單比查不到多了 218 個 tokens（958 − 740），證實 token 主要花在 tool_result。

踩雷紀錄

問狀態，卻連客戶和單價都說了
第 3 題只問狀態，第 5 題只要取消，模型都列出了客戶名稱、品項或單價。第 1 題問「出貨了嗎」就沒有。lookup_order 回傳整筆，模型拿到什麼就可能說什麼。再加上 IDOR（見 0012），猜到 5 位數字就可能看到別家的採購內容。這不能靠模型自己節制，要在 Component 6 從 tool 的回傳值解決。
模型補了資料裡沒有的東西
第 5 題叫使用者聯絡「order support or fulfilment team」，第 2 題說有「confirmation email」可以幫忙查。這個團隊不在任何資料裡，tool 也只能用編號查。不嚴重，但正是答案品質 eval 要抓的東西。
要取消訂單，卻先查了一次
這題不查也能回答，多花了一輪。推測跟 description 寫的「Use this whenever the user asks about a specific order」有關，但只跑一次還不能確定。這是 Component 3 的 trajectory 題目。
end_turn 卻沒有文字：決定 raise
原本回傳空字串，使用者只會看到一片空白。手上也沒有新資訊，再問一次沒有意義（見 0011）。所以改成 raise AgentLoopError，只有空白字元也算。
這些都只是「跑一次」的觀察
每題只跑了一次，問法也不同，所以看不出模型每次是否都會這樣。eval 要同一題跑很多次才算數。is_error 的路徑也還沒碰過真的 API，模型這幾次都沒有叫錯 tool 或傳錯參數，留給 Component 3 去打。
