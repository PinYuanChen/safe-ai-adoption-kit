NOTE 0013第 1 課錯誤與邊界已理解2026-11-04

工具當掉時：細節留給自己，模型只拿通用訊息

一句話：同一個 exception 分兩路走：完整細節印給開發者看，模型只拿一段固定的訊息。

背景

第一版的 except 直接把 str(e) 放進 tool_result。agent 確實不會當掉了，測試也全綠，看起來很完美。直到我們模擬了一下模型實際會讀到什麼。

觀念

try / except

try:
    result = lookup_order(order_id, orders)
    ...
except Exception as e:      # 出錯時跑這裡，e 是那個 exception
    ...

try 只包住可能出錯的呼叫，參數驗證留在外面。範圍越小，越不會接住不該接的錯。

一個 exception，兩個去處

為什麼是 except Exception，而不是 except KeyError

在 tool 的邊界，我無法預知會出什麼錯，所以全部接住，agent 才不會當掉。代價是：lookup_order 本身有 bug 時，這裡會把它包成普通的 tool 錯誤，看起來還是「正常」運作。所以 test_tools.py 那些直接測 lookup_order 的測試很重要：它們不經過這個 try，bug 會直接讓測試失敗。

stdout 和 stderr

print(f"lookup_order failed: {type(e).__name__}: {e}", file=sys.stderr)

最終回答會印到 stdout。錯誤細節走 stderr，兩者才不會混在一起。

第一個安全測試

class BrokenStore:
    def __iter__(self):
        raise RuntimeError("SECRET-INTERNAL-DETAIL")

result = run_tool(block, BrokenStore())
assert "SECRET-INTERNAL-DETAIL" not in result["content"]

for order in orders 會呼叫物件的 __iter__，所以它一被走訪就爆炸，用來模擬「資料來源壞掉」。訊息用一個明顯的標記字串，測試就能檢查它有沒有跑進 content。這個測試不是在測功能做對了沒，而是在測不該發生的事有沒有發生，算是 Component 3 紅隊測試的雛形。

踩雷紀錄

str(e) 把內部細節送給了模型
模擬兩種錯誤後，模型實際讀到的是： 
Error occurred while looking up order: 'order_id'
Error occurred while looking up order: could not open /srv/harbor/orders.db as user svc_orders: permission denied
第二行的路徑和帳號（模擬的）可能被模型轉述給使用者，也可能被攻擊者故意觸發來套資訊。第一行則會誤導模型：它會以為是自己傳的 order_id 有問題，白白重試一輪。
細節只給了模型，我自己反而看不到
當時 exception 的資訊只進了 tool_result，沒有任何地方留底。真的出事時，我只會聽到「系統暫時無法使用」。所以才加了印到 stderr 那一行。
BrokenStore 跑進了正式 code
測試用的 BrokenStore 同時出現在 agent_loop.py。測試用的是測試檔自己那份，所以全綠，完全沒發現。測試工具不該混進正式程式，以後讀 code 的人會以為它有用途。刪掉了。
